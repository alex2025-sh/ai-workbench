# 引擎执行流程：通俗版

本文用一个比喻加一个真实例子，把引擎从头讲一遍，每一步都说明为什么这样设计，最后附代码地图，方便对照着读。完整设计见 `docs/workflow-engine.md`。

---

## 一、先建立直觉：引擎就是"办事大厅"

把一次 workflow 运行（run）想象成一份**纸质档案**，档案里夹着一张流程图，图上每个节点都有自己的状态。

| 引擎里的概念 | 办事大厅里的对应物 |
|---|---|
| `wf_run` 一行 | 档案封面：现在办到哪了、成功还是取消 |
| `wf_node_run` | 档案里每一步的进度：待办、办理中、等人回复、已完成 |
| `wf_job` | 贴在墙上的**待办便签**："现在去执行节点 X"、"48 小时后提醒"、"去发一张 Lark 卡片" |
| run 行锁 | 档案柜**只有一把钥匙**，谁拿着钥匙谁才能改这份档案 |
| 认领 + 租约 | 在便签上签名："我在办，10 分钟内办完" |
| 凭证 `attempt` | 签名旁的**序号**，每换一个人认领就加 1 |

整个引擎只有一条铁律：

> **改档案（流程状态、便签状态）必须拿着钥匙改，而且要快；慢的事情（调接口、调 LLM、发卡片）放下钥匙再去做。**

后面所有设计都是围绕这条铁律展开的。

## 二、跟着一个真实例子走一遍

以 VIP 工单提醒为例，流程是：`start → ask_rm（人工选择，48 小时超时）→ done`。

### 第 1 幕：启动（`StartRun`）

cron 扫到一张新工单，调用 `StartRun`，这一步只开**一个事务**：

```
拿钥匙
  ├─ 新建档案（wf_run）和每个节点的进度行（wf_node_run，全部 pending）
  ├─ start 节点直接完成，沿边传播：ask_rm 的入边都满足了 → 变成 ready
  └─ 贴便签：「执行 ask_rm」（wf_job, kind=execute, 现在到期）
提交，还钥匙
```

然后**就地**把刚贴的便签拿去办（`drive`），不等定时器来扫。

**为什么就地办？** 早期版本是后台线程每秒扫一次表。空闲时也在白扫，多个进程扫来扫去还在 MySQL 上互相死锁。流程本来就是由事件推着走的，所以事件来了就顺手往下推，推到停下来为止，省掉了轮询。

### 第 2 幕：执行一个节点（最核心的三步）

便签「执行 ask_rm」到手后，分**三步**：

```
① 认领（短事务，拿钥匙）
   ├─ 检查便签：还没人办？已经到期？节点确实还在等执行？
   ├─ 在便签上签名：attempt 0→1（这就是我的凭证），租约 = 超时 + 30 秒
   └─ 节点标为 running，执行次数 +1
   提交，还钥匙

② 执行（不拿钥匙，慢慢做）
   └─ 调分配服务找到 RM、渲染卡片……可能要好几秒

③ 提交结果（短事务，拿钥匙）
   ├─ 先核对：便签上的序号还是我的 1 吗？（是 → 继续；不是 → 结果作废，什么都不改）
   ├─ ask_rm 是人工节点 → 节点改成 waiting
   ├─ 贴便签：「48 小时后超时」（timeout job）
   ├─ 贴便签：「发 Lark 卡片」（effect job）
   ├─ 贴便签：「同步任务状态到任务中心」（sync_task effect）
   └─ 原来那张「执行 ask_rm」便签划掉（done）
   提交，还钥匙
```

**为什么要拆成三步，而不是一个事务包到底？** 第 ② 步可能要几秒到几分钟（LLM 最长 10 分钟）。如果一直拿着钥匙，这份档案的所有其他操作都会被堵住，比如 RM 正好点了卡片；数据库连接也会被长时间占住。所以钥匙只在 ① 和 ③ 这两个**毫秒级**的瞬间拿。

**为什么 ③ 要核对序号？** 因为 ② 期间没拿钥匙，世界可能已经变了。具体见第三节"僵尸"场景。

### 第 3 幕：发卡片（effect）

第 ③ 步提交后，「发卡片」便签马上被拿去办。它也是认领、调用 Lark、提交三步，和第 2 幕一样。

**为什么不在第 ② 步直接发卡片，而要另贴一张便签？** 设想直接发：卡片在第 ② 步发出，第 ③ 步还没提交，RM 手快已经点了；这时节点还不是 waiting，点击就会被拒绝成"该节点已处理"。所以规则是**先提交状态，再对外触达**：节点确定 waiting 之后才发卡片。发送失败也只重试发卡片，不会把整个节点重新执行一遍。

### 第 4 幕：等待（什么都不发生）

现在档案停在 `ask_rm = waiting`，墙上只剩一张「48 小时后超时」便签。**引擎此时不跑任何东西，也不查数据库**，是真正的闲置。

### 第 5 幕：两种结局，抢同一把钥匙

**结局 A：RM 点了「已处理」**（`Signal`）

```
拿钥匙
  ├─ 校验：run 还在跑？节点还是 waiting？轮次对得上？选项合法？
  ├─ 撕掉「超时」便签（cancelled）
  ├─ ask_rm 完成，走 ok 端口 → done 节点 ready → …… → 全部节点有结论 → run 成功
  └─ 贴便签：同步任务中心（solved）
提交，还钥匙
```

**结局 B：48 小时到了，xxl-job 的 tick 来了**（`ProcessDue` → `fire`）

```
拿钥匙
  ├─ 超时便签还是 pending？节点还在 waiting？
  ├─ 是 → 节点走 timeout 端口，继续传播
  └─ 否（已经被点了）→ 便签作废，什么都不做
提交，还钥匙
```

**关键在于：两者如果同时发生，会抢同一把钥匙。** 先拿到的一方生效，后到的一方拿到钥匙后发现"节点已经不是 waiting 了"，于是放弃。这就是锁 run 行的意义：**把并发变成排队，排在后面的一方看到的永远是最新状态。**

定时器（timer/timeout）没有外部 IO，所以**不需要认领和租约**，一个事务就做完。

## 三、"为什么要这么复杂"：三个出事场景

只要执行（第 ② 步）发生在锁外，就会有下面三类问题。引擎的每个机制都对应其中一个。

### 场景 1：进程在执行到一半时被 kill

A 认领了「执行 s」，正在调 skill 时进程被 OOM 杀掉了。

- **便签上有租约**（`locked_until`）。到期后 tick 发现"签了名但过期了"，就允许别人重新认领。
- 崩溃的那一次**计入执行次数**，相当于一次超时失败。如果一个节点每次都把进程搞崩，次数用尽后就按失败处理，不会无限重试。
- 如果是**正常退出**（发版），执行被打断后结果仍会提交，便签放回队列，执行次数退回，不算这个节点的错。

### 场景 2：僵尸，老执行者"诈尸"

```
时间 →
A: 认领(attempt=1) ── 调 skill，卡了很久 ─────────────────── 终于返回，想提交
B:                         租约过期 → 认领(attempt=2) → 执行 → 提交成功 ✔
```

A 回来时，钥匙拿到手一看，便签上的序号已经是 2，不是自己手里的 1，于是**丢弃结果，什么都不改**。如果没有这个序号核对，A 会把 B 已经推进过的流程再推进一遍，下游节点就会被执行两次。

同一个进程里的两个 goroutine 也一样，靠序号区分，不靠 owner 名字。重构前的一个 bug 就出在这里：同一进程的 owner 相同，两个 goroutine 有可能拿到同一个凭证。

**那 A 调过的外部接口怎么办？** 已经发生的副作用收不回来，所以所有外部动作都带**幂等键** `run_id:node_id:iteration`，由下游去重。引擎的保证是：步骤**至少执行一次**，流程图的推进**恰好一次**。

### 场景 3：执行期间流程被取消

ask_rm 还在执行，工单已经被关闭，`Cancel` 拿钥匙把 run 改成 cancelled，并撕掉所有待办便签。执行者回来提交时，发现便签已被撕或 run 已取消，结果作废。

## 四、为什么所有修改都走一个 `update`

前面每一个"拿钥匙"的步骤都是同一个形状：

```go
update(runID, jobID, func(s *runState) {
    // 只在内存里改：s.complete(...) / s.claim(...) / s.cancelJobs(...)
})
// update 统一负责：开事务 → 锁 run → 读节点和便签 → 调 fn → flush 一次性写回 → 提交
```

这样设计是为了下面四点：

1. **规则只写一次。** 锁顺序、读最新状态、写回、提交都在一个地方，新增入口（比如以后的 rework、snooze）不可能忘记加锁。
2. **便签不用再单独加锁。** 改便签的人一定拿着 run 的钥匙，所以拿到钥匙后读到的便签就是最新的。重构前额外需要的 CAS 认领、回读、`SELECT … FOR UPDATE` 锁 job 行，全都省掉了。
3. **业务逻辑里没有 SQL。** `complete`、`wait`、`fail` 只改内存，读起来就是状态机。
4. **事务重试不会泄漏脏结果。** 遇到死锁时整个事务重来，只有**最终提交成功的那一次**的结果会被返回（`transact[T]`）。

## 五、谁来按"继续"键：drive 和 tick

```
事件入口（StartRun / Signal / Cancel）        xxl-job 每 10~30 秒的 tick（ProcessDue）
          │                                          │
          ▼                                          ▼
     提交后拿到新便签 ────────►  drive  ◄──────  扫出到期的便签（定时器、重试、租约过期）
                                  │
                       并发处理（最多 4 个），新产生的便签接着处理
                       直到：遇到等待点 / 流程结束 / 用完 100 个预算
                       用不完的留在表里，等下一次 tick
```

- **就地推进**：事件来了顺手推到底，延迟最低。
- **tick 兜底**：负责"将来的事"（定时、退避重试）和"被遗弃的事"（崩溃留下的便签）。
- **预算和并发上限**：防止一个事件把当前请求拖得太久。

所以 `wf_job` 表里平时只躺着两类便签：**还没到时间的**，和**需要恢复的**。

## 六、一张表记住全部设计

| 机制 | 解决什么问题 | 不这样做会怎样 |
|---|---|---|
| 锁 run 行 | 同一 run 的并发修改（点击和超时、两个分支汇合） | 两边同时生效，流程走两条路 |
| 执行放在事务外 | 慢 IO 不能占着锁 | 一个 LLM 调用就把整份档案和数据库连接堵住 |
| job 表（便签） | 将来的事、崩溃后的恢复 | 进程一挂，流程永远卡住 |
| 认领 + 租约 | 执行期间别人不要重复执行；崩溃后能被接手 | 要么重复执行，要么没人接手 |
| 凭证核对 | 僵尸执行者的结果 | 下游被调度两次 |
| 幂等键 | 至少执行一次带来的重复调用 | 重复发卡片、重复调接口 |
| 先提交再发卡片（effect） | 外部看到的状态不能领先于数据库 | 点击被误拒、发送失败要重做整个节点 |
| 统一的 `update` 和 `flush` | 规则只存在于一个地方 | 每个入口各写一遍，迟早漏掉一个 |

## 七、对照代码读的顺序

1. `internal/flow/engine/engine.go`：`StartRun`、`Signal`、`Cancel`，三个入口都很短，先看它们怎么调用 `update`。
2. `internal/flow/engine/state.go`：`update`、`lock`、`flush`，就是第四节说的"统一形状"；然后看 `complete`、`wait`、`finish` 这些状态转换。
3. `internal/flow/engine/jobs.go`：`execute` 依次调用 `startExecution`（认领）、`invoke`（执行）、`finishExecution`（提交），对应第 2 幕；`fire` 对应第 5 幕结局 B；`effect` 对应第 3 幕。
4. `internal/flow/engine/drive.go`：`drive` 和 `ProcessDue`，对应第五节。
5. `internal/flow/engine/core.go`：`propagate`，负责"节点完成后谁变成 ready"，是纯函数。

读的时候，每看到一个函数，就问自己三个问题：它**在不在锁里**？它**改了哪几张表**？它**怎么防备别人同时在动同一个 run**？三个问题都能答出来，这个引擎就算吃透了。
